# CareConnect Mobile architecture

React Native CLI Android app for CAREGIVER with strict TypeScript. The user requested Flutter replacement on 01/11/2026, then explicitly replaced the Expo approach with React Native CLI and limited the target to Android. Earlier Expo/Flutter design and progress documents are historical; this runtime decision supersedes their platform setup.

## Runtime boundaries

App.tsx mounts shared providers; src/app/navigation.tsx composes auth guard, four tabs (Today, Assigned visits, Work schedule, Profile) and detail/form stacks. Work schedule owns three sections: Day agenda, Register for shifts and Time off. The separate Work shifts tab and list stack route have been removed; WorkShift remains a registration detail/form route and ProviderSchedule remains the linked availability/cancellation route. Requests, retained deposits, certificates and signed-in devices are secondary destinations. Assigned visits shows date filters inline and includes a Cancelled tab. The legacy History stack route opens the same cancelled list. src/core contains HTTP/session, boundary parsers, memory resources/mutation hooks, bilingual copy fragments, theme/shared controls and foreground device access. Core never imports features. Feature-owned models/repositories/screens now include booking-requests, earnings and availability; the profile schedule module only reexports compatibility types. BE/FE code is never imported or executed by the app.

All business traffic uses the gateway /api/v1. ApiClient unwraps code=200/result; Page models retain server totals and pagination. Unknown JSON is parsed into typed models at boundaries. Domain text stays as provided. No API payload logging, persisted patient cache, offline mutation queue or patient database. Cache-Control:no-store is sent. Report images open as HTTPS links rather than disk-cached native previews. The native documents adapter uses open mode with no local copies or long-term file access grants.

## Session

Unified /auth/login and /auth/refresh with X-Client-Type:mobile supersede deprecated /auth/mobile aliases and web cookie/CSRF transport. Refresh tokens are in namespaced Android Keystore-backed Keychain storage, access tokens only in memory. GET /users/me checks ACTIVE and CAREGIVER. Backend authorizes every actual request. Retired Expo SecureStore entries are not imported; first CLI launch requires sign-in.

The sign-in recovery entry now matches FE's `login-page.tsx` (07/11/2026): Reset password is a right-aligned text link below the password and above Sign in, with a48dp target, link semantics and press feedback. It opens the existing Forgot route and is disabled during a pending login. It reuses the bilingual resetPassword copy and the existing gateway forgot/reset APIs. Account registration is not added, per the user's corrected request; caregiver access remains center-provisioned.

Storage writes are serialized. Session epochs reject responses from an earlier account/logout. Concurrent 401 requests share one rotation, retrying authentication failure once. Timeouts/5xx on mutations are not automatically retried. Transient restore failure retains the secure refresh token and shows retry; invalid credentials/role clear the session. Logout removes protected UI, forms, memory data and polling even if server revocation fails; revocation uncertainty is surfaced.

## Domain contracts

BookingOccurrence is an assigned visit. CareSession is actual care. Provider Schedule is assigned work availability, never simulated visit progress. Detail snapshots/services may be absent from list DTOs or hidden by scope. No secondary patient API bypasses snapshot visibility. The full-profile entry requires a visible occurrence snapshot and recipient ID; it then reads the backend's assigned-caregiver view described below. Masked phones are not callable.

The work-shifts feature owns caregiver registration and supplies content embedded in Work schedule → Register. The four groups match current FE `work/shifts/shift-signup.tsx`: Open excludes the caregiver's own PENDING/APPROVED registrations; Pending and Approved contain only corresponding registrations whose Vietnam start is still in the future; History contains the remaining registrations. The backend's OPEN is center-wide and may still include this caregiver's approved shift while other places remain; it is not a caregiver-specific candidate count. Mobile reads every required OPEN/registration page (size100, no arbitrary page cap), applies those ownership/time partitions, then computes counts and display pages of20. Date/type/vacancy filters remain server filters. Unlike the FE's first100 cap, later candidates cannot disappear behind already-registered rows or earlier server pages. Registration cards preserve actual states/versions. Work dates/times and registration deadlines are shown in Vietnam time. Detail reads the profile and scans all registration pages to detect an active PENDING/APPROVED registration. POST /work-shifts/{id}/registrations sends caregiverNote only (max2000); success remains PENDING until BE approval. Confirmed DELETE /work-shifts/registrations/{id}?version=... is available only for PENDING. APPROVED registrations offer a withdrawal entry to the linked availability schedule: that screen reads all necessary pages for the actual schedule/version and performs its own confirmed cancellation; it never uses registration DELETE for approved records. Embedded registration summaries preserve effective shift status, cancellation reasons and linked-schedule metadata when a shift is no longer readable. Readiness includes the center status; BE is authoritative for overlap/time-off, start/deadline/capacity and all writes.

Historical deviation (01/11/2026): non-null date filters caused PostgreSQL42P18/HTTP503, so the old board scanned all OPEN pages and filtered locally. Current BE commit eec3231 (05/11/2026) adds typed nullable predicates and effective lifecycle filtering. This update retires that workaround and uses the current server filter/page contract. The fix is source-verified; no live BE mutation or database migration is part of this update.

Registration detail explicitly labels the write Send registration to your center. The parsed POST response is retained while refreshing the detail, so a failed follow-up GET cannot expose a second submit action after an acknowledged PENDING result. Actions remain locked until reconciliation. Pending records explain manager review and link to the integrated Pending filter via a consumed typed `registrationView` parameter. This is registration for an existing center shift; the current DTO accepts only caregiverNote and does not support proposing arbitrary dates/times.

Known registration refusal codes use a feature-supplied bilingual ErrorBox message, matching FE's domain error mapping. In particular4401 means overlapping approved availability and directs the caregiver to choose another shift; it must not be presented as an optimistic-version conflict. Uncertain transport/write results still take priority over domain copy, and409 reconciliation locks remain in force. No conflicting schedule is cancelled or overwritten automatically.

The integrated registration board omits the center introductory line and the global Register for shift button above the process guide. Registration remains available on individual open-shift cards. The RegisterShift compatibility route retains its paginated chooser reusing the same caregiver-specific candidate workflow. Candidate cards show Open for registration with Register; own active registrations appear only in Pending/Approved (or History after their start). Selecting a candidate opens WorkShift for the real submission; entering the chooser itself never sends a registration. Empty copy explains that already-registered shifts are in the other groups without falsely asserting that the center has no OPEN shifts.

Visit statuses follow BookingService booking spec v1.0 (2026-11-02): a caregiver sees SCHEDULED, ACKNOWLEDGED, IN_PROGRESS, COMPLETED, CANCELLED, CAREGIVER_MISSED (formerly MISSED) and CUSTOMER_NO_SHOW; RESERVED, PENDING_ASSIGNMENT and EXPIRED exist before the customer pays and only have labels.

Acknowledgement (Nhận buổi) posts /booking-occurrences/{id}/acknowledge before the captured check-in window opens. Since BE c2377eb, a SCHEDULED visit can check in directly during that window. An ACKNOWLEDGED visit shows the disabled opening time before the window. The exclusive check-in closing and end boundaries, pending no-show decisions, existing sessions and replacement requests suppress a new start. The click handler rechecks readiness and BE authorizes each write. Starting posts /care-sessions and navigates using the returned sessionId. Only IN_PROGRESS permits task/note edits. DONE counts as completed and SKIPPED requires a reason. Explicit checkout has confirmation and BE owns the resulting session and occurrence state.

Customer booking requests are separate from occurrence acknowledgment. GET /bookings/caregiver-requests paginates owner-scoped previews. Current BE also permits recipientName, customerName and allergies from the booking snapshot; mobile parses and displays those fields only when present, without reading forbidden full booking/patient detail or inventing clinical defaults. Full address/phone remain outside this preview. Accept posts /bookings/{id}/caregiver-accept without an invented version/body; decline sends a required trimmed reason≤1000. Parsed returned states determine waiting-payment, rejection or center-handover messaging. A request is not a scheduled visit until backend payment/assignment rules permit it. Deadline/conflict5116 and unknown writes require explicit reconciliation; absence from the pending list is not proof of a specific decision. Decline text remains until explicit dismissal. No caregiver-forbidden booking/patient-detail read is used.

Customer-absence reporting posts /booking-occurrences/{id}/no-show-reports with10–1000 characters, only inside the actual configured check-in window. Pending absence waits for the center; mobile exposes no manager decision. Acknowledge is offered only before start. Home now presents a compact care banner, server-backed Today/Completed counts and the paginated daily visit list without filtering out a separate focus card. It uses the Vietnam day for both from/to; completed counts come from the backend totalElements, never a visible-page sum. Home restores a compact Needs your attention card immediately above today's schedule when the authoritative pending booking-request total is positive. Reply opens Assigned visits → Needs response. Its count comes from GET /bookings/caregiver-requests (page0,size1), not notification unread totals or the visible request page; failure/loading remain explicit. The standalone Customer requests navigation card is removed from Assigned visits. Needs response embeds the existing accept/decline workflow and separately lists SCHEDULED occurrences from the Vietnam day onward for center-assignment acknowledgment, as in current FE. The tab badge combines the server pending-request and SCHEDULED totals only when both reads succeed. Other visit ranges remain available; booking requests never masquerade as occurrences. Only a successful zero-total response shows the empty state with Register and Upcoming actions. Register selects Work schedule → Register; View all/Upcoming pass and consume typed list-range parameters so prior filters/history do not override the chosen destination. Loading/read errors remain distinct from an empty day.

The earnings feature is a read-only retained-deposit ledger: GET /deposit-forfeitures and /summary with required from/to Instants. Vietnam-calendar month/year starts are converted to Instants; filtering is by inclusive recorded-at time, not care time. Summary caregiverAmount comes from the backend, never a sum of the visible page, salary estimate or withdrawal balance.

Report lookup scans all booking pages for sessionId. The editor matches FE with two text areas: summary (required, max 4000) and recommendations (optional, max 2000). Overall condition remains an explicit required choice because the BE DTO requires it; no clinical default is invented. Existing meal/medication/mobility/mood notes remain in the typed model and update payload, and in submitted report read-only details, so simplifying the editor does not erase previous content. PUT includes optimistic version. A saved draft ID is retained before upload/submit. Submission requires ENDED and explicit confirmation, and SUBMITTED becomes read-only. BE emits REPORT_SUBMITTED to the booking's customer; mobile does not send separate SMS/email or choose recipients outside backend scope. No clinical condition or vital value is preselected. Max five JPEG/PNG/WebP report photos, each <=10 MB; server validates content/scope.

Unknown-result writes/conflicts block repeats until server reconciliation. Forms remain in memory on failure and guard leaving unsaved content. Backend remains final authority for states, rules, time and authorization.

Availability cancellation uses the existing caregiver contract: `PATCH /caregivers/schedules/{id}/status` with `status: CANCELLED`, a trimmed required reason (maximum 500 characters) and the schedule's actual optimistic `version`. Schedule list/write responses are parsed at the profile boundary; no version is invented. The provider screen labels SCHEDULED as an open availability slot without changing Booking's assigned-visit labels. As in FE, cancellation is offered for SCHEDULED slots whose Vietnam-local end time has not passed; BE rechecks ownership, version, state and assigned bookings and rejects booked slots (409/code4415). Successful cancellation also cancels the linked registration in BE and can reopen the work shift; mobile does not perform those secondary writes itself.

Cancellation requires an explicit reason/confirmation modal. Pending writes lock the form, failed inputs stay in memory, closing a dirty modal requires discard confirmation and uncertain/conflicting writes cannot repeat until an explicit fresh read reconciles the selected slot. No automatic write retry, local-success simulation or direct Booking cancellation is used.

Availability also provides a phone week/day agenda combining all required schedule/visit pages with own time-off intervals. Time off uses GET/POST /caregivers/{id}/time-offs and confirmed DELETE /caregivers/{id}/time-offs/{timeOffId}; no version is invented. Whole-day intervals use Vietnam midnight through exclusive midnight after the last day. Duration is positive and≤30 days, optional reason≤500; caregiver cannot override overlaps with assigned visits. Unknown create/delete reconciliation retains the attempted interval, independently of edits to the form.

Time-off start/end date fields now each include a48dp calendar button (07/11/2026), compared with FE `work/time-off/time-off-form.tsx`'s DatePicker controls. Both use the existing typed Android calendar adapter and retain manual ISO entry. Each selection changes only that field; cancellation changes nothing, calendar failures show bilingual manual-entry recovery and no selection submits a write. The native dialog opens on the existing field date; ISO calendar dates retain the existing Vietnam UTC+07 conversion on explicit Save. Date picking locks save/close/repeated opens and keeps dirty-form and uncertain-write reconciliation intact. No new date/time default, API rule or dependency is introduced. The native picker was already part of the maintained Android source; reinstall the development app if that native module is not present in the installed binary.

Work schedule uses one scroll surface per active section. Agenda week ranges and card dates omit the year visually; underlying ISO dates/queries remain unchanged. Visit cards show patient name, address, date/time and actual status plus View details; availability cards have no patient/address and use their domain label without invented data. Notes and explanatory availability text are excluded from these summary cards but retained in details. View details opens the linked availability detail without launching a cancellation form; the explicit Withdraw approved shift entry supplies `cancel: true` to open that form. Embedded Time off retains the existing modal, dirty-form guard and uncertain-write checkpoints; switching sections is locked while its form is open, a write is pending or its outcome needs reconciliation. Day-agenda time-off links select the integrated Time off section.

Profile professional fields/services remain center-managed. Account name/phone use Identity's numeric10–11-digit contract. Passwords follow the backend strength rule and72-byte UTF-8 bound; confirmation is required locally. Successful change clears secure/in-memory session and protected UI immediately because BE revokes all sessions. Signed-in devices use owner-scoped GET /auth/sessions and confirmed DELETE /auth/sessions/{id}; current-session deletion clears the mobile session.

Device rows parse the backend's `ip` and show browser/OS inferred from `userAgent`, relative last activity and the authoritative `isCurrent` badge; unknown agents retain an unknown-device label rather than guessed device names or raw technical identifiers. The current session sorts first and has no row sign-out action. The list initially shows five rows with View all/Show less. Confirmed Sign out all other devices requires exactly one identified current session and sequentially revokes only other IDs from that displayed snapshot, using the existing per-session endpoint (BE has no bulk API). A failure stops the sequence; explicit successful reconciliation is required after partial/unknown outcomes, with no automatic batch replay or fabricated success. A fresh list determines which sessions remain.

Own avatar/certificate actions use Provider media APIs and original document URIs without copied files. Avatar selection chooses the newest valid HTTPS IMAGE by displayOrder, respecting expiry; image upload≤5MB JPEG/PNG/WebP. Certificate metadata uses actual versions and allows equal issue/expiry dates; creating/updating returns to backend PENDING. PDF/JPEG/PNG attachments≤10MB use a checkpointed certificate ID before upload. Uncertain creates cannot be correlated by display name and remain blocked; uncertain uploads require fresh server links and explicit removal/review of the pending selection before another upload. Professional verification controls are never exposed to caregiver.

Profile presentation mirrors the FE's six completeness criteria: server avatar, Identity phone, Provider dateOfBirth/bio, assigned services and at least one non-rejected certificate that has not expired in Vietnam time. This local display metric does not grant verification or registration eligibility. An additional owner-scoped certificate read supplies that criterion; if it fails, the metric is withheld and a retry is shown without hiding the rest of the profile. Provider dateOfBirth/gender are parsed at the repository boundary; missing experience remains missing rather than a fabricated zero. Pending avatar content URIs may preview locally but do not count as a saved photo. Deposits follow assigned services, Security expands to existing password/device routes, language controls are last. ## Calendar and notification lifecycle

Provider workDate/startTime/endTime remain Vietnam local UTC+07. Booking timestamps remain Instants and format in device timezone; from/to query dates and today's count use the Vietnam calendar. Home/schedule refresh on resume/date changes.

Foreground NotificationFeed polls the unread count every30 seconds for the notification bell badge. The inbox loads its own pages. Polls serialize; background/disposal invalidates late results. Logout resets the protected subtree/feed. Owner-scoped inbox supports unread filtering, read/unread, selected read-state/deletion, individual deletion and confirmed clear-read. Mutation counts are parsed; unread count is freshly read, never fabricated. Pages clamp after filtered totals shrink. Resolved occurrence links navigate directly; CAREGIVER_REQUEST/BOOKING opens Assigned visits → Needs response with the linked booking ID; other booking references scan authorized occurrences instead of reading forbidden booking detail.

Pending-request counts and the visible response list refresh every30 seconds while focused and foreground, and on focus/resume. Accept/decline reconciliation refreshes the count from BE; uncertain writes retain the existing reconciliation latch and block switching response filters until resolved. These read polls never replay a write. BE creates CAREGIVER_REQUEST for the selected caregiver; mobile consumes that notification rather than creating a second one.

BE exposes SSE but no FCM registration contract; this implementation provides the foreground inbox and unread badge.
